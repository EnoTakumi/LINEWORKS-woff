## 2. 確認前提の検証(求職者・求人・トーク履歴・タスク・ダッシュボード)

| 検討中の案 | 判定 | 理由 |
|---|---|---|
| 求職者 = 既存流用(Leads/Contacts/CV) | **推奨しない(新規 `LWZ_Candidates` を推奨)** | Leads: 会社軸の営業リードで、変換(Convert)前提。サンプル10件が他デモと共用。Contacts: 作れるが、希望条件・LINE識別など17項目前後を共用タブに足すことになり、全デモのレイアウトに影響する。しかも「デモ用データだけ一括削除」が他のサンプルと混ざる。CV: 履歴書向けではなく、持ち主不明の1件がある。**新規なら既存タブへの変更ゼロ**、タブ追加は1つ(115→116) |
| 求人 = 新規 | 妥当 | 既存に該当なし |
| トーク履歴 = 新規 | 妥当 | 1メッセージ=1レコード。件数が多くなるため専用タブが適切 |
| 対応タスク = 標準 Tasks 流用 | **妥当(条件付き)** | Tasks に項目を足さず、「関連データ」を求職者にして使う。デモ識別は項目ではなくタグ(LWZ_DEMO)と件名接頭辞【LW】。**要確認**: Tasks の関連データにカスタムモジュールを選べるか(作成後に実機で検証) |
| ダッシュボード = Analytics | **妥当だが作成は手作業** | 使えるMCPにダッシュボード作成のツールが無い。レポート/ダッシュボードは人が画面で作る(LWZ-024は「保留(人作業)」) |

## 8. ダミーデータ・初期化の方針(④で実施。ここでは作らない)

- 規模: 求職者10名 / 求人15件 / トーク履歴30件。氏名・会社名・電話・メールはすべて架空(電話は 090-0000-xxxx、メールは example.com ドメイン、LINEユーザーIDは `U`+架空32桁)。
- 意図的に混ぜるもの: 未紐付けの会話(求職者=空)4〜5件 / 対応漏れ(未対応のまま数日放置+`LWZ_Overdue`)4〜5件 / 希望条件を含む会話(勤務地・職種・年収の発言)10件前後。
- 新規4タブの全レコードに `LWZ_Data_Category=デモ用`。追加する架空の Accounts(8件前後)にはタグ `LWZ_DEMO`。
